# Taste
- When reporting a bug, asks "why is this happening" — expects a root-cause explanation (what the code was doing wrong, why the backend/service rejected it), not just a patch. Confidence: 0.85
- Reports bugs as a single terse line describing the symptom ("when i upload an image it's not saving why", "can you tell me why the images are not uploading whats the reason?", "i was not getting a proper failed logs alsoo") or by pasting raw console/device logs verbatim with no framing ("got this error log" + stack of log lines); expects the agent to trace the codebase, read the log closely, and diagnose autonomously rather than ask for more detail first. Confidence: 0.8
- Expects failures to be visible and diagnosable: complains when a broken operation produces no proper failure logs, and wants the real error surfaced (genuine log/alert with the underlying reason) instead of silent fallbacks or generic "please try again" messages. Confidence: 0.75
- Pastes raw client-side API error log lines verbatim ("apiClient.ts:116 [ApiClient] POST /location/add failed (status 400): ... native: {...code: BAD_REQUEST}") and asks "why this error was coming" — wants the request payload traced back to each call site, which ones send invalid/missing fields, and whether it's a frontend or backend fault. Confidence: 0.7
- Wants a verdict on ownership of a bug ("is it a frontend issue or backend issue", "this was backend or frontend issue?"), not just a list of suspects: give a direct, argued answer naming the guilty side up front, backed by the specific code/library evidence, and only then the fix. Confidence: 0.8
- Asks terse yes/no state/behavior/deployment questions about the running system ("tell me selfie verification was active or not", "does it checking the selfie verification of profile setup?", "to use it does backend team neeed to deploy jar or no need") and "where does this value come from" questions ("from which endpoint im getting the ngrok url for selfie verification?"); expects a leading direct answer followed by the concrete evidence chain (HTTP status/response body, exact endpoints and call order, file:line, where the flag/URL is stored and set, and which sources are empty/no-ops) rather than hedged possibilities. Confidence: 0.85
- Wants user-facing error copy that is human and actionable, not the raw backend string: asks "what message should I show when I got this error?" when the server returns a bare "Photo rejected." / BAD_REQUEST — expects a friendly title + body that tells the user what to do differently. Confidence: 0.7
- When a diagnosis finds contributors on both sides, wants their own (client/frontend) side fully fixed first — "please fix the frontend bug from our side then will find where it was failing" — before continuing to chase the backend cause. Confidence: 0.6
- Rejects fail-open fallbacks in verification/validation paths: explicitly says to "remove the fall back of selfie verification part" — wants a single strict call that surfaces the real error and blocks progression, not retries with alternate params/endpoints, normalization chains, or fabricated success responses. Confidence: 0.8
- When a validation rule is added to one flow, expects the same rule mirrored in the parallel flow ("same follows in edit profile upload images also") — onboarding and Edit Profile must behave consistently. Confidence: 0.7
- Requires parity across user segments, not just flows: on hearing a rule only worked for one group ("this was working for woman only for men its not checking the images uploaded") insists it "should follow for every gender" — validation must run identically for every account, with no gender/user-type condition gating it. Confidence: 0.7
- Signals urgency and wants execution in the current turn — "ok please do it now" — rather than a proposal, plan, or clarifying questions. Confidence: 0.6
- Wants validation enforced at the point of action rather than deferred to the Next/progress step: an item the backend rejected must not be left in the UI state (slot/grid) or allowed to advance. Confidence: 0.6
- Expects expected/business rejections (4xx answers like "this photo does not match your verified selfie") to be shown to the user in a popup/alert instead of being swallowed or blowing up — "for this error show the popup message as well instead of failing", restated as "when got this error show the popup message in the screen" — the failed operation must stop and explain itself, never fail silently. Confidence: 0.9
- Judges a UI fix by the visible result on screen, not by the code change: when told "there is already a popup", pushes back that the popup must literally render for the user (screenshots of the dev overlay are the evidence). Before declaring something fixed, trace whether the message can actually be displayed (e.g. alert mounted inside a modal that is closed first) rather than assuming the handler runs. Confidence: 0.7
- Asks whether config/credentials are hardcoded ("are we using it hardcoded?", "that token will be added in backend or database") and expects the exact location of the secret in the repo — every file/line that references it, with the value masked — plus whether the app bundle/committed config leaks it. Confidence: 0.7
- Wants credentials/secrets owned server-side (env variable, backend config, or DB) rather than embedded in the mobile client; treats a token shipped in the app as wrong and expects it removed and moved to the backend/bot host contract. Confidence: 0.6
- Dislikes the red dev error overlay (LogBox) firing for routine business rejections; expects those to be handled quietly (console.log-level) with the user-facing popup as the real signal, while genuine failures (network drops, 5xx) stay loud via console.error. Confidence: 0.65
